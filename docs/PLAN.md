# Rust rewrite plan

This plan covers porting the `elyosh` projects to Rust on top of Bevy. Phase 1 covers the three building blocks:
**Aeron**, **imuse** and **landru**.

## 0. What we are porting

Findings that shape the plan:

- **landru and imuse are host-agnostic.** They contain no SDL or Aeron code. They talk to the outside world only through
  callback tables (`LandruHost`, `LandruRenderSink`, `SoundActionFunc`, `ImuseHost`). The games glue them to Aeron in
  their `*_runtime/integration` adapters.
- **landru has no blocking loops.** Its modal loops are already a cooperative task stack (`landru_task_run_frame`),
  which maps onto a Bevy system called once per frame.
- **imuse is driven by the host's clock.** The host calls `imuse_advance(usec)` once per frame, and the audio side pulls
  samples with `imuse_mix_*`. imuse starts no threads of its own.
- **Aeron is mostly replaced by Bevy, not ported.** What must be ported:
  - pure logic: VFS + ISO9660, the YAML config tree, surfaces and palettes, and the asset decoders;
  - Bevy plugins: the ordered layer compositor, the input snapshot, the audio mixer, 2D and UI.
- **The games use only part of the building blocks.**

  | Building block | Public surface | OpenXW uses | OpenTIE uses | OpenXvT / OpenXWA |
  |---|---|---|---|---|
  | landru | ~1124 functions | 359 | 377 | not used |
  | imuse | 76 functions | 37 | 45 | not used |
  | Aeron | ~610 functions | 318 | 345 | 343 / 286 |

  The full inventory is generated by `just usage`; see §3.
- **There are no upstream tests.** Verification is differential against the C build (§6).
- **Licensing:** everything upstream is GPL-3.0, so this workspace is GPL-3.0 as well.

## 1. Ground rules

### 1.1 No `unsafe`, no C wrappers

- `[workspace.lints.rust] unsafe_code = "forbid"`, inherited by every crate.
- **No dependency that wraps a C/C++ library**: no FFmpeg, FluidSynth, Munt, SC-55, libyaml or zstd-sys. Use
  pure-Rust crates or port the code.
- **The one unavoidable exception is the platform layer.** Window, GPU and audio drivers are reached through OS C
  APIs (Vulkan/Metal/DX12, X11/Wayland, ALSA/CoreAudio/WASAPI). That happens inside Bevy, wgpu, winit and cpal, never
  in our code.
- **Prefer the pure-Rust option wherever Bevy features offer one.** For example, zstd for KTX2 via `ruzstd`.

### 1.2 Port only what is used

- A function is ported if it is:
  - **called by at least one of the four games** at their pinned commits, or
  - **reached from such a function** inside the building block. This includes callbacks the block installs into
    itself, such as actor kinds, task vtables and backend tables.
- Everything else is skipped and listed as "unused" in the crate's `USAGE.toml` (§3). A function becomes a porting
  candidate the moment a game starts using it, and `just upstream-status` reports that.
- Consequences already known:
  - **imuse `state_io.c`** (save and restore of the music engine state) is not called by any game, so it is not
    ported.
  - **imuse MT-32 and SC-55 backends** are dropped by decision. Pure-Rust MT-32 (`moont`) remains a possible later
    addition; see §4.1.
  - **Aeron:** `surface.h` (direct use), `atlas_pack`, `gltf_mesh`, `text2d` and `random` are unused by all four games.
    Only code reachable from used functions comes along.

### 1.3 Integer mappings become types

| Upstream pattern | Rust translation |
|---|---|
| closed set of `#define`/C `enum` values used in code | `enum` (`#[repr(uN)]` when the numeric value matters) |
| value **read from data files** (FILM opcodes, FOURCCs, VOC block types, SysEx ops…) | `#[repr(uN)] enum` + `TryFrom<uN>`. Unknown values become an `Unknown(uN)` catch-all where upstream tolerates them, or an error where upstream rejects them. |
| set of OR-able bits (`AF_*`, `FF_*`, `INPUT_*`, wave start flags, modifier masks) | `bitflags!` |
| integer carrying a payload (`ImuseParam` 0x1100..0x1700 with the channel in the low byte; opcode ≥30 meaning "callback pointer") | enum with data, e.g. `Param::PartVolume { channel }`, `Cmd::Op(Opcode) \| Cmd::Callback(CallbackId)` |
| negative error codes | `Result<T, Error>` with a `thiserror` enum |
| sentinel values (`-1` none, `0` wildcard) | `Option<T>` or dedicated variants |
| `int16_t` "BoolResult" | `bool` |
| inline magic numbers (`0x5200` Insert key, VESA `0x101`, paint ops 0–4) | named enums (`DosScanCode`, `VesaMode`, `PaintOp`…) |

Enums derive with `num_enum` (`TryFromPrimitive`, `#[num_enum(catch_all)]`), which generates safe code.

### 1.4 Staying close to the original structure

- **One Rust module per C translation unit, with the same name.** Each module starts with
  `//! Port of landru/actor.c, include/landru/actor.h`. Private headers become `pub(crate)` items.
  - Where §1.5 splits a C file into a state part and a render part, both halves keep the C file's name under
    `state/` and `render/`.
- **Function names drop the C prefix, since the module path supplies it.** `xactor_Alloc_Actor` becomes
  `actor::alloc_actor` with `#[doc(alias = "xactor_Alloc_Actor")]`. Upstream tracking reads these aliases to know which
  C functions are ported (§3).
- **Reverse-engineering annotations are kept verbatim** as doc comments, e.g. `/// FUNCTION: TIE95 0xD2F54`.
- **Global mutable state is grouped into a context struct.** File-scope `static`s and `*_gbl` externs become one
  context (`Landru`, `Imuse`) with a sub-struct per C module. Functions take `&mut Landru` / `&mut Imuse`.
- **Raw pointers and intrusive lists become typed indices into arenas** (`slotmap`).
- **Struct-prefix inheritance and `void*` vtables become an enum of kinds or a trait.** Examples: `enum ActorKind`,
  `enum Task`, `trait MidiBackend`.
- **Game callbacks become enum ids dispatched through a game trait, not stored closures.**
  - Upstream stores per-actor and per-input `draw`/`update`/`user` function pointers. In Rust each record stores an
    enum id (`G::ActorFn`).
  - The game implements, for example, `trait LandruGame { fn actor_user(&mut self, l: &mut Landru, ..);
    fn actor_draw(&self, l: &Landru, canvas: &mut Canvas, ..) }`.
  - This lets the compiler enforce §1.5 (draw takes `&`), keeps state serializable and needs no `Rc`/`RefCell`.
- **Byte reinterpretation becomes parsing.** Code like `*(int16_t*)p` and packed structs becomes explicit little-endian
  parsing over `&[u8]` at load time.
- **Every intentional behaviour change is logged.** It gets a `// DEVIATION:` comment plus an entry in the crate's
  `DEVIATIONS.md`. Example: the imuse LP64 pointer-truncation bugs, which disappear in Rust.

### 1.5 Simulation and rendering are separate

The goal is that game logic and state can be developed and tested without any renderer.

- **The state is plain data.**
  - Simulation state (game state, landru actors and films, imuse sequencer state) lives in Bevy-free structs.
  - It is changed **only** by step functions with explicit inputs: `step(&mut self, input: &InputFrame, dt)`.
  - Nothing inside a step reads the host clock, polls input, or depends on rendering progress.
- **Rendering reads state and never writes it.**
  - Every render function takes the state as `&State`.
  - A renderer may own and mutate its **own** caches (canvas buffers, dirty rects, GPU images, synth chips), but
    never simulation state.
  - Interior mutability (`Cell`, `RefCell`, `Mutex`) is banned in simulation state types through clippy
    `disallowed_types` in the simulation modules, so `&` really means read-only.
- **Rendering happens in two stages, and only the second one uses Bevy.**

  ```
  landru:  Landru (state) ──render──▶ PresentedFrame { pixels: Vec<u8>, palette: [Rgb; 256] } ──aeron/Bevy──▶ GPU texture on screen
  imuse:   Imuse (state)  ──render──▶ PCM samples (Vec<i16>)                                  ──aeron/cpal──▶ audio device
  ```

  1. **landru and imuse render to plain memory.** landru rasterises sprites, text, palette fades and wipes into an
     8-bit indexed framebuffer, exactly as the DOS original drew into VGA memory. imuse synthesises the OPL3 chip and
     mixes the digital tracks into a sample buffer.
     - This is plain computation on byte arrays. It needs no GPU, window or audio device, so it needs no Bevy.
     - It is also how upstream works: landru and imuse contain no SDL code, and the host (`landru_layer.c`,
       `audio/output.c`) uploads the buffer.
  2. **Presentation happens in `aeron`, inside Bevy.** Bevy reads the finished buffer and puts it on screen (texture
     upload + compositor layer) or on the speakers (cpal stream). That is the only Bevy-dependent step.
  - **Why the first stage stays outside Bevy:** pixel-exact behaviour. Palette cycling, palette fades, the 26 wipe
    modes, RLE deltas and dirty-rect semantics are naturally exact in software, and that exactness is what lets us
    compare frame hashes against the C build (§6). A GPU-native redraw would only approximate it.
  - **A second renderer stays possible.** Because state is separate, a Bevy-native high-resolution renderer (sprites
    and text drawn by Bevy from `&Landru`, like OpenTIE's remaster path over `LandruRenderSink`) can be added later in
    `aeron` or a game crate. It would read the same state alongside the software one.
- Both stages follow the same rule: landru's rasteriser reads `&Landru` and writes only `LandruRaster`; imuse's
  synthesis reads commands and writes only its synth state; Bevy reads only the finished buffers.
- **Bookkeeping that upstream does while drawing moves out.**
  - **Refresh flags:** `xactor_Non_Refresh_Actor`, which clears refresh flags after drawing, becomes per-object
    **change counters**. The simulation increments the counter when an object changes. The rasteriser compares it with
    the last value it drew, stored in its own cache.
  - **Polling mid-draw:** `xtimer_Often()`, which polls the timer and input inside draw loops, is removed from
    rendering. Input is sampled once per step.
  - Both are logged as deviations.
- **Bevy schedule.**
  - Simulation systems run in a `Simulation` set (`FixedUpdate`/`Update`) and are the only systems with `ResMut`
    access to simulation resources.
  - Presentation systems run in a later `Presentation` set with `Res` access only.
  - A schedule test asserts that no `Presentation` system has write access to a simulation resource.
- **What this enables.**
  - Simulation tests: scripted inputs and assertions on state, without ever calling a renderer.
  - Rasteriser tests: state in, frame hash out.
  - The upstream frame loop is preserved as `step` followed by `render`.

## 2. Workspace layout

```
justfile                    # every command-line action (§5)
Cargo.toml                  # [workspace], shared dependencies and lints
crates/
  aeron/                    # lib; `bevy` feature on by default. vfs/config/asset build without it (headless tests)
  imuse/                    # lib; Bevy-free (mirrors upstream)
  landru/                   # lib; Bevy-free (mirrors upstream)
bin/
  openxw/ opentie/ openxvt/ openxwa/   # game bin crates (stubs until phase 2)
tools/devtool/              # Rust CLI behind the upstream / usage / harness recipes; never invoked directly
harness/                    # C reference programs built against upstream (§6); not part of cargo
.upstream/                  # git clones of the 7 upstream repos (gitignored)
docs/
```

- **Dependency direction mirrors upstream:**
  - landru and imuse depend on neither Bevy nor Aeron;
  - Aeron does not depend on landru or imuse;
  - game crates own the glue.
- **The Bevy-free rule is "if possible", not absolute.** Upstream already keeps these libraries host-agnostic, so being
  Bevy-free costs us nothing. If a later need makes a direct Bevy dependency clearly simpler, we revisit it (e.g. an
  optional `bevy` feature exposing a Plugin).
- **Runnable demos are crate examples with dev-dependencies.** For instance `crates/landru/examples/landru_player.rs`
  has dev-deps on `aeron` and `imuse`. This keeps one crate per upstream project.
- **Bevy:** 0.20, pinned in `[workspace.dependencies]` with only the features we use. `bevy_audio` is disabled (see §4.3).

## 3. Upstream tracking and usage inventory

Each crate records the last upstream commit it fully reflects:

```toml
[package.metadata.upstream]
repository = "https://github.com/elyosh/landru"
commit = "bbc73c360f7ccf97b87687c3201abab2af0b0fac"
```

A crate has no `commit` until its first function is ported. Porting then starts at the snapshot commit in §0, which
becomes the crate's first pin.

- **`crates/<name>/USAGE.toml` is the generated inventory of used functions.**
  - It is produced by `just usage` and committed. For each C function of the block (static ones included, third-party
    code excluded) it records its status (`used` by a game, `reached` from a used function, or `unused`), which games
    use it, whether it is public, and whether it is ported (detected through `#[doc(alias)]`, §9 #13).
  - `tools/devtool` scans C without preprocessing (§9 #19), so the inventory errs towards porting too much.
  - Because it is committed, changes in game usage show up in review.
- **`just upstream-status` filters upstream changes down to what affects us.**
  1. It fetches the 7 repos into `.upstream/` and lists the commits since each pin.
  2. It uses git's function-aware diff hunks to name the C functions each commit touched.
  3. It splits those into three groups:
     - **ported** functions that changed: these need catching up;
     - **unported** functions that changed: ignored;
     - functions **newly used** by a game: these need porting.
  - This keeps catch-up work focused, given that Aeron alone has ~13 commits a week.
- **Catch-up workflow:**
  1. Port at the pinned commit.
  2. Catch up in batches, one PR per batch.
  3. In the same PR, bump the pin with `just upstream-bump`.

## 4. Building-block plans

### 4.1 imuse (port first: smallest, headless, easy to verify)

- **Public API**
  - `Imuse::new(host, config, backend)`.
  - The `commands`, `lolevel`, `hilevel` and `groups` modules mirror the upstream headers.
  - `advance(elapsed)` keeps the upstream timing tiers:
    - the core tick is 8000 µs of real time, counted as 8060 µs of logical time;
    - in X-Wing timing mode the tick is 3433 µs instead;
    - fades and triggers run at 60 Hz, ducking at 10 Hz;
    - catch-up is capped at 8 ticks.
- **Host trait** (`ImuseHost`, passed to every call that reads sound data or can fire a callback)
  - `sound(id) -> Option<Arc<[u8]>>` replaces `getSoundPtrFunc` (and `getSoundSizeFunc`: the slice has a length).
  - `SoundId` is a newtype.
  - Trigger and defer callbacks are game-defined `CallbackId`s. The host's `trigger_callback(&mut self, &mut Imuse,
    …)` runs inside the tick and may issue commands, as upstream callbacks do (§9 #21).
- **Layout.** Same two-part split as landru:
  - `state/` holds the engine: `seq`, `players`, `slots`, `sustain`, `triggers`, `fades`, `groups`, `commands`,
    `dispatch`, `tracks`, `xwing`, plus the game-thread work upstream also does there: the wave `mixer` and the
    producer end of `wave_renderer`, the DOS93 AdLib driver (which only queues register writes), and the queue
    ends of the other backends.
  - `render/` holds what runs on the audio thread: `fm4_driver` + OPL3, `gmidi_driver` + rustysynth, the AdLib
    chip, and the consumer end of `wave_renderer`.
- **Threading and separation.** Upstream already matches §1.5:
  - the `Imuse` engine is simulation (sequencer, players, triggers, fades, digital-track dispatch), advanced only by
    `advance(dt)`;
  - the `ImuseRenderer` is rendering, running in the audio callback and owning the synth chips and the output ring;
  - the two are joined by one-way SPSC rings (`rtrb`).
  - **To verify while porting:** the wave renderer's `filledHalves` feedback must not make simulation progress depend
    on audio-device consumption. Dispatch runs on logical time; an underrun produces silence, never back-pressure.
  - The renderer can be driven offline (no audio device) to produce WAVs for tests.
- **Backends** (additive Cargo features):

  | Feature | Upstream | Plan |
  |---|---|---|
  | `fm4` (default) | `fm4_driver.c`, `fm4_data.c`, `midi_fm4_opl3.c` | port. Default for TIE; plays X-Wing's General MIDI and AdLib arrangements on OPL3 |
  | `xwing-adlib` (default) | `midi_xwing_adlib.c` | port. X-Wing 1994 AdLib arrangement |
  | OPL3 chip | `third_party/nuked-opl3-fast` | try the pure-Rust `nuked-opl3` crate against the C register and PCM trace. If it isn't bit-exact with the "fast" configuration, port `opl3.c` (~2k LOC) |
  | `soundfont` | `gmidi_driver.c` + FluidSynth | port `gmidi_driver.c`; `rustysynth` replaces FluidSynth. This is the "SoundFont" option both games offer |
  | — | `midi_mt32.c`, `midi_nuked_sc55.cpp` | **dropped** |
  | — | `state_io.c` | **not ported** (unused by the games) |

- **Port order:**
  1. `utils`, `timer`
  2. `files`, `filelist`
  3. `seq`
  4. `players`, `slots`, `sustain`, `triggers`, `fades`, `groups`
  5. `midi`, `midi_backend`, `fm4_*`, OPL3
  6. `commands`, `lolevel`, `hilevel`
  7. the wave path
  8. `xwing`, `midi_xwing_adlib`
  9. `gmidi_driver` + rustysynth
- **Exit criterion.** The headless example `imuse_render` writes a WAV whose PCM hash and OPL register trace match the
  C build tick for tick.

### 4.2 landru

- **Internals are split in two parts.**

  ```
  crates/landru/src/
    state/      # part 1: state + the logic that updates it. `Landru` struct, step(&mut self, &InputFrame, dt)
      actor.rs film.rs view.rs viewadd.rs pal.rs fade.rs input.rs dialog.rs task.rs timer.rs res.rs …
    render/     # part 2: rendering. `LandruRaster` struct, render(&mut self, &Landru) -> PresentedFrame
      actor.rs film.rs viewadd.rs pal.rs fade.rs input.rs dialog.rs canvas.rs bitmap.rs delta.rs font.rs paint.rs …
    formats/    # pure parsers shared by both (LFD, FILM, DELT, ANIM, PLTT, FONT, TEXT, input trees)
  ```

  - **Part 1, `state`:** the `Landru` struct (one sub-state per C module) and all update logic: move view,
    update/user callbacks, films, actors, tasks, timer, palette and fade *progress*, and sound requests.
  - **Part 2, `render`:** the `LandruRaster` struct, which holds the canvas, diff and buffer bitmaps, dirty rects,
    change-counter caches, background captures (`actback`), cursor save-under and the previous frame for wipes. It
    also holds all erase/draw/rasterise code.
  - **`render` only ever receives `&Landru`.** Both parts are always compiled; there is no feature flag. `state` never
    imports from `render`; a devtool check enforces this. State tests simply never call the renderer.
  - **Each C file maps to a file of the same name in `state/`, `render/`, or both.** For example, `actor.c` splits
    into `state/actor.rs` (update, user, z-sort, movement) and `render/actor.rs` (`xactor_Draw_Actors` and the actor
    kinds' draw functions). Pure drawing modules (`bitmap`, `delta`, `color`, `flip`, `scale`, `canvas`, `dirty`,
    `paint`, `font` glyph drawing) live only in `render/`. The `//! Port of` headers make the devtool map one C file
    to both halves (§3).
  - **The `viewadd` frame task splits too.** Its update half (move view → update → user callbacks → sounds) goes to
    `state/viewadd.rs`, and its erase → draw → fade wipe → present half goes to `render/viewadd.rs`.
- **Host traits.**
  - The simulation host keeps files, the clock, and input, delivered as an explicit `InputFrame` rather than polled
    callbacks.
  - Palette and video presentation leave the host trait, because they are outputs of the rasteriser.
  - `LandruRenderSink` (TIE's high-resolution snapshot path) becomes a read-only view over `&Landru`.
  - Sound actions are emitted as a list of `SoundAction` requests per step.
- **Open check:** confirm no simulation path reads back canvas pixels. Hit-testing uses rectangles, but this still
  needs an audit.
- **Game variant: one crate, runtime `GameVariant { Xw, Tie }`.**
  - Measured divergence: **17% of lines** (3.5k of 20.6k) sit inside `LANDRU_GAME_*` blocks, plus 1.2k lines of
    variant-only modules. Most of the divergence is concentrated in `input`, `canvas`, `font`, `dialog`, `stream`,
    `sound`.
  - Two crates would duplicate the shared 83% and break the 1:1 mapping with upstream tracking.
  - Small `#if` blocks become `match variant`. Functions that diverge heavily become two functions, `foo_xw` and
    `foo_tie`, inside the same module.
  - Variant-only struct fields become variant enums.
  - Under §1.2, variant-specific code is ported only where its game uses it.
  - `LANDRU_MODERN` is always on: both games enable it.
  - **Revisit at the end of M3.** If the per-variant `match`es end up dominating, split out `landru_xw`/`landru_tie`
    on top of a shared `landru` core.
- **Memory.** `memhdl`/`memptr`/`memcom` become typed arena keys and owned buffers.
- **Formats** each get a pure parser with unit tests on synthetic data:
  - containers: LFD, FILM, DELT, ANIM;
  - graphics: PLTT, FONT;
  - text and UI: TEXT, the TIE input/dialog trees.
- **Control flow.** `task.c` becomes `Vec<Task>` with `enum Task { View, Dialog, Fade }`. Keep the upstream semantics
  of `run_frame`, `next_wake_delay_us` and the 250 Hz PIT emulation.
- **Port order:**
  1. `error`, `rect`, `file`, `res`, `paragrp`, `stream`
  2. `pal`, `bitmap`, `delta`, `color`, `flip`, `scale`, `remap`
  3. `canvas`, `surface`, `vesa`, `video`, `dirty`
  4. `timer`, `task`
  5. actors, `film`, `view`, `viewadd`
  6. `fade`, `font`, `paint`, `cursor`, `style`
  7. `io`, input and widgets, dialogs
  8. `sound`, `render`
- **Exit criterion.** Headless playback of a FILM from TIE and from XW data. The per-frame presented-framebuffer +
  palette hashes match the C build.

| FSR3, imgui, crash handlers, `scene_capture`, `netprobe` | dropped | — |

Phase key:
- **A:** headless foundations.
- **B:** the runtime needed to show landru and play imuse in a window.
- **C:** game ports.
- **D:** later, on demand.

### 4.4 The DirectX "compat" layer: native code instead

- **Why upstream has it.**
  - OpenXvT and OpenXWA are reconstructions of Win32 executables, and so are the 1998 Windows code paths inside
    OpenXW and OpenTIE.
  - The recovered C code calls DirectDraw, Direct3D 5, DirectSound, DirectInput, WinMM and DirectPlay exactly as the
    original binaries did: COM interfaces, vtables, HRESULTs, binary-exact structs.
  - Aeron's `compat/` reimplements those interfaces on SDL so the recovered code compiles **verbatim**. That trick only
    makes sense when you keep the original C.
- **In Rust we translate every call site anyway, so no emulation layer is needed.** Each DirectX use becomes native
  Rust/Bevy:

  | DirectX in the game code | Native replacement |
  |---|---|
  | DirectDraw surfaces, palettes, flips | `Vec<u8>` + palette submitted as a compositor layer |
  | Direct3D 5 execute buffers of pre-transformed triangles | Bevy meshes / the 2D pipeline |
  | DirectSound buffers | mixer voices |
  | DirectInput | `InputSnapshot` |
  | WinMM CD audio | an audio stream of the music files |
  | DirectPlay | native Rust networking, **not** wire-compatible with the original or upstream |

- **What remains is behaviour the game logic relies on.** Examples:
  - a streaming loop that polls a DirectSound play cursor and writes ahead of it;
  - palette changes that take effect at the next flip.
- Where the "used functions" inventory shows such a dependency, `aeron` gets a small native type with those
  semantics. These are plain Rust structs, not COM.
- This is decided per game, when that game is ported.

## 5. Task runner: `just`

Every command-line action is a `just` recipe. Recipes call `cargo`, `git` and `cmake` directly. Logic too involved for
a recipe (C function extraction, usage scanning, trace comparison) lives in `tools/devtool`, a small Rust binary that
only the recipes invoke.

| Recipe | Action |
|---|---|
| `just` | list recipes |
| `just build` / `check` / `test` / `doc` | cargo over the workspace |
| `just fmt` / `lint` | rustfmt, clippy `-D warnings` |
| `just ci` | everything CI runs |
| `just example <crate> <name> [args]` | run a crate example |
| `just upstream-fetch` | clone or update the 7 repos in `.upstream/` |
| `just upstream-status [crate]` | commits since the pin, split into changed-ported, changed-unported and newly-used functions |
| `just upstream-diff <crate> [file\|function]` | upstream diff since the pin |
| `just upstream-bump <crate> <sha>` | move the pin |
| `just usage [crate]` | regenerate `USAGE.toml` from the games at their pinned commits |
| `just harness-build` | build the C reference programs at the pinned commits |
| `just traces <crate>` | regenerate reference traces (needs game data) |
| `just test-data` | run the tests that need game data (every edition under the Justfile's `games_dir`; `TOG_DATA_XW` / `TOG_DATA_TIE` / `TOG_DATA_XVT` / `TOG_DATA_XWA` override) |

## 6. Verification

There are no upstream tests, so we compare the port against the original C code (differential testing):

- **`harness/` produces reference traces.** It holds C programs built against the **pinned** upstream commit. Each one
  replays a deterministic scenario and writes one trace line per tick or frame:
  - imuse: OPL register writes + PCM block hashes;
  - landru: the hash of each presented frame and palette.
- **Rust tests compare against those traces.** Only hashes are committed, never game data.
- **Game data is user-supplied** through `TOG_DATA_XW` / `TOG_DATA_TIE` / `TOG_DATA_XVT` / `TOG_DATA_XWA`: a
  `PATH`-style list of install folders and GOG disc images per game. Tests skip when it is absent. `just test-data`
  fills the lists from the `games_dir` hardcoded in the Justfile, covering every edition (XW and TIE: DOS floppy,
  Collector's CD disc image, 1998 Windows; XvT; XWA).
- **Format parsers get unit tests** on synthetic data built in the tests.
- **Simulation tests** (§1.5) drive `step` with scripted `InputFrame`s and assert on state, without calling the
  renderer and without Bevy or an audio device. **Rasteriser tests** feed a state and compare frame hashes.
- **Traces are regenerated at each pin bump.**

## 8. Risks

- **Aeron churn.** Ported lazily; the function-level status report (§3) filters out changes to code we don't use.
- **Callback-heavy landru vs the borrow checker.** Settle the patterns in §1.4 in the first modules, before they spread.
- **Game draw callbacks that write state.** OpenXW and OpenTIE register many callbacks with landru: 208 actor draw
  functions, 225 input draw functions, 162 custom actors and 385 actor "user" callbacks. Every draw callback must be
  audited at game-port time. Any state write moves into the corresponding user or update callback.
- **The original game loops interleave simulation and rendering.** The flight engines will need the same split as
  landru. This is the largest structural deviation from upstream; it is accepted (decision 10).
- **OPL3 exactness.** Verify the pure-Rust crate against the trace before relying on it.
- **3D visual parity** with Aeron's custom shaders is approximate on Bevy PBR. This affects phase C only.
